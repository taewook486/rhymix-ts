# SPEC-LEGACY-PARITY-002 — design

> 데이터 모델과 경계에 관한 결정. 각 결정은 권고안과 대안, 그리고 되돌리기 어려운 정도를 적는다.
> 구현 세부(함수 이름·파일 구조)는 run-phase 가 정하며, 여기서는 관찰 가능한 동작에 영향을 주는
> 선택만 다룬다.

## D1 — 사이트 포인트 설정의 저장 형태 (REQ-MEMB-011·012·014·015)

- 현재: `SitePointConfig` 단일 행에 열 4개(`schema.prisma:680`).
- 필요: 포인트 이름, 레벨 체계(최대 레벨·레벨별 기준점·아이콘 세트), 행위별 기본 금액 16종
  (로그인·문서·댓글·업로드·다운로드(+작성자)·읽기(+작성자)·추천/비추천 × 문서/댓글 × 행위자/대상),
  행위별 일수 제한 11종, 삭제 시 회수 3종, 공지 제외 2종, 다운로드·읽기 제한 2종.
- **권고**: 스칼라 설정(포인트 이름, 최대 레벨, 아이콘 세트, 제한 토글, 회수 토글)은 `SitePointConfig` 열로
  추가하고, 행위별 금액·일수 제한은 행위 키를 가진 구조(예: 행위 키 → `{ amount, dayLimit }`)로 한 곳에 둔다.
  레벨별 기준점은 정수 배열로 둔다. 모든 값은 Zod 스키마(`packages/point/src/schemas.ts`)가 검증한다.
- 기본값: 모든 행위 금액 0, 일수 제한 0(제한 없음). 설정하기 전에는 지급 결과가 지금과 같다.
- 대안: 전부 JSON 한 열. 마이그레이션은 쉽지만 DB 수준 기본값·제약이 사라진다.
- 되돌리기: 열 추가는 가산적이라 쉽다. 기존 4개 열은 그대로 둔다.

## D2 — 게시판별 금액의 "설정 안 함" 표현 (REQ-MEMB-013) — 결정됨

- 현재: `Board.pointPer*` 6개 열이 `Int @default(0)` 이고(`schema.prisma:789-794`), 문서·댓글 작성은 0 이면
  지급하지 않는다. 이 의미는 `SPEC-POINT-001` REQ-POINT-005 가 정했다("Default 0 means no point awarded").
  레거시는 모듈별 값이 비어 있으면 사이트 기본값을 쓴다.
- 문제: 0 이 "설정 안 함"과 "이 게시판은 0점"을 동시에 뜻한다. 사이트 기본값을 도입하면 둘을
  구분해야 한다.
- **결정(2026-11-28 사용자 결정)**: 6개 열을 nullable 로 바꾸고 `NULL` = 사이트 기본값 사용, `0` = 명시적
  0점으로 정한다. 기존 행의 0 은 `NULL` 로 옮긴다(레거시 의미와 같음). 이로써 REQ-POINT-005 의 의미를
  뒤집는다(spec.md §7).
- 근거 측정: 개발 DB `boards` 는 2행이고, 6개 열 중 하나라도 0 이 아닌 행은 0개다
  (2026-11-28 오케스트레이터 실행, `select count(*), sum(case when … <> 0 …) from boards` → `2|0`). 이 열을
  설정하는 화면이 지금까지 없었다는 코드 사실(`research.md` §2.1)과 일치한다. 운영 DB 는 측정하지 않았으므로,
  다른 DB 에 이전을 적용하기 전에 같은 질의로 0 이 아닌 행을 세어 기록하고, 0 이 아닌 값은 그대로 둔다.
- 지급 결과: 사이트 기본 금액의 기본값이 0 이므로(D1), 관리자가 사이트 기본값을 설정하기 전까지 NULL 과 0 의
  지급 결과는 같다. 이전 직후 문서·댓글 지급 결과는 바뀌지 않는다.
- 행위 키 확장: 레거시 모듈 설정 키는 15종(로그인 제외)이고 기존 열은 6종이다. 부족한 키는 D1 과 같은 행위
  키 구조로 게시판에 둔다. 기존 6개 열을 그 구조로 옮길지 유지할지는 run-phase M1 에서 정하되, 어느 쪽이든
  "NULL = 사이트 기본값"을 지킨다.
- 되돌리기: 0 → NULL 이전은 데이터 변경이다. 롤백 마이그레이션은 NULL → 0 으로 되돌리고 열을 다시
  `NOT NULL DEFAULT 0` 으로 바꾼다. 사이트 기본값이 0 인 동안에는 두 표현의 지급 결과가 같다.

## D3 — 회원 이용 제한·관리 메모의 저장 (REQ-MEMB-007)

- 필요: 이용 제한 종료일, 제한 사유, 거부 사유, 관리자 메모.
- **권고**: `User` 에 nullable 열 4개를 추가한다. 이용 제한 종료일은 로그인 판정에서 조회해야 하므로
  JSON(`extraVars`)에 두지 않는다. 종료일은 날짜(시각 없음)로 저장하고, 사이트 시간대의 오늘이 종료일 이하인
  동안 제한한다(레거시 `substr(limit_date,0,8) >= date('Ymd')` 와 같은 경계).
- 로그인 판정 위치: 기존 status 게이트(`packages/auth/src/login.ts:264-270`)와 같은 자리에서, 같은
  `failClosed` 경로로 거부한다. 응답은 다른 실패와 구분되지 않는다(REQ-AUTH-051).
- 노출: 네 값 모두 관리자 화면에만 보인다. 레거시는 제한·거부 사유를 로그인 실패 메시지에 붙이지만
  (`member.controller.php:2787-2798`), rhymix-ts 는 단일 실패 응답 불변식을 우선한다(spec.md §4 의도적 차이).
- 대안: 별도 `MemberRestriction` 테이블(이력 보존). 레거시도 현재값만 두므로 이번 판에서는 열로 충분하다.
- 되돌리기: 가산적 열 추가.

## D4 — 인증 로그의 데이터 원천 (REQ-MEMB-008·009)

- **권고**: 새 테이블 없이 `LoginAttempt` 를 조회한다. 결과 유형 필터는 enum 4종
  (`SUCCESS`·`INVALID_CREDENTIALS`·`STATUS_BLOCKED`·`RATE_LIMITED`)이다.
- 회원 매칭: `identifier` 가 회원의 아이디 또는 이메일과 일치하면 그 회원으로 표시한다. 회원 정보
  (아이디·이메일·이름·닉네임)로 검색하면 일치하는 회원의 아이디·이메일 집합으로 `identifier` 를
  찾는다. 레거시가 `member_auth_log` 를 `member` 와 left join 하는 것과 같은 결과다.
- 표시 제한: 비밀번호 등 비밀 값은 `LoginAttempt` 에 없으므로 노출 위험이 없다. 식별자 원문은
  관리자에게만 보인다.
- 정리(REQ-MEMB-009): 삭제 기준 시각은 "지금 − 일수 × 24시간"이고, 그보다 이른 행만 지운다. 허용 최소 일수는
  `max(1, ceil(로그인 실패 집계 시간창(분) / 1440))` 이다. 시간창보다 짧은 기간으로 지우면 진행 중인 무차별
  대입 집계가 초기화되기 때문이다. 시간창(REQ-MEMB-017)에 상한을 두지 않으므로 최소 일수도 시간창을 따라
  늘어난다. 닉네임 변경 기록은 집계와 무관하므로 최소 1일만 적용한다.
- 감사: 삭제 작업은 REQ-MEMB-023 에 따라 AdminLog 를 남긴다.

## D5 — 회원 기능 토글의 저장과 소비 (REQ-MEMB-010) — 결정됨

- 저장(이 SPEC): 기존 기능 설정(`FeatureSettingsSchema`, `server/api/routers/admin/settings.ts:102`)에 키 7종을
  추가한다. 기본값은 켜짐(레거시 기본값과 같음). 관리자 기능 설정 탭에 토글 7개를 항상 보여 준다.
- 소비(`SPEC-LEGACY-PARITY-008`): 방문자 화면이 이 설정을 읽어 메뉴 노출과 직접 접근 거부를 판단한다.
  2026-11-28 사용자 결정에 따라 이 SPEC 은 008 의 구현 여부와 관계없이 닫을 수 있다.
- 설정 키 이름은 run-phase M1 에서 정하고, 008 이 읽을 수 있도록 progress.md 에 키 목록을 기록한다.

## D6 — 회원 수정의 쓰기 경로 (REQ-MEMB-002~006)

- 상태·관리자 여부·닉네임은 기존 부품(`changeUserStatus`·`toggleAdminRole`·`updateNickname` 의 판정)을
  거쳐 바꾼다. 같은 판정을 다시 구현하지 않는다. 이렇게 해야 세션 무효화·마지막 관리자 보호·닉네임
  정책이 한 관문에 남는다.
- 한 번의 저장은 원자적이어야 한다(REQ-MEMB-003). 여러 부품을 순서대로 부르는 방식이면 검증을 먼저
  모두 끝낸 뒤 하나의 트랜잭션에서 쓴다.
- 감사 기록: tRPC mutation 으로 구현하면 `auditLogger` 가 남기되, 대상 열 `AdminLog.target` 에 `user:<id>` 가
  들어가도록 프로시저가 대상을 공급한다(지금 `auditLogger` 는 빈 문자열을 쓴다 — plan.md M8). Server Action 으로
  구현하면 같은 형식으로 직접 남긴다(REQ-MEMB-023 대상 형식 표). 입력의 비밀번호 키는 마스킹한다.

## D7 — 레벨 계산 (REQ-MEMB-011)

- 기준점 배열 `[t1, t2, …, tn]` 의 k 번째 값은 레벨 k 의 기준점이다. **레벨 = 잔액이 도달한(잔액 이하인) 가장
  높은 기준점의 단계**이고, 최대 레벨을 넘지 않는다. 잔액이 `t1` 보다 작거나 기준점이 비어 있으면 레벨 1 이다.
  예: 기준점 `[0, 100, 500]` 에서 잔액 99 → 레벨 1, 100 → 2, 499 → 2, 500 → 3.
- 레거시와의 차이(의도적): 레거시 `PointModel::getLevel`(`modules/point/point.model.php:107-118`)은
  `level_step[1]` 미만이면 레벨 0 을 돌려주는 0 기반이다. rhymix-ts 는 `defaultLevel` 최소값 1
  (`packages/point/src/schemas.ts:7`)과 기존 자리표시자의 반환값(레벨 1)에 맞춰 1 기반으로 둔다.
- 레벨 아이콘: 아이콘 세트 하나를 고르고, 세트 안에서 레벨 번호로 이미지를 찾는다(레거시와 같은 방식).
  레거시 아이콘 세트 이미지는 옮기지 않는다.
- 기존 시그니처 `getLevel(_memberId)` 는 회원 잔액을 읽도록 바뀐다. 호출자가 없으므로 시그니처
  변경 영향은 패키지 내부에 그친다(run-phase 에서 호출자 0건을 재확인).

## D8 — 시간 경계 (REQ-MEMB-007·009·012)

- "하루"의 경계(로그인 포인트, 이용 제한 종료일)는 사이트 시간대(`Site.timeZone`, `schema.prisma:31`)의
  달력 날짜로 판단한다. 레거시는 서버 시간대의 `date('Ymd')` 를 쓴다.
- 일수 제한(`*_limit`)과 기록 삭제 기준은 달력 날짜가 아니라 24시간 단위 경과 시간으로 판단한다. 레거시
  `regdate < RX_TIME - limit * 86400` 과 같다: 정확히 N×24시간이 지난 대상은 아직 지급 대상이다.
