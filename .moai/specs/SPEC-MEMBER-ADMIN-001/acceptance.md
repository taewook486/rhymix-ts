# SPEC-MEMBER-ADMIN-001 — 인수 기준 (Acceptance Criteria, GEARS)

> [HARD] 모든 시나리오의 관찰 기준은 **런타임 영속 + 실제 동작 반영**이다. "화면에 필드가 있다"/
> "저장 버튼을 누르면 200이 온다"만으로는 통과하지 않는다 — 저장 후 **새로고침(또는 재조회)** 하여
> 값이 유지되는 것, 그리고 검증/차단 로직이 관련된 항목은 그 값이 **실제로 동작에 영향을 주는 것**까지
> 확인해야 한다(SPEC-MENU-001 §3 "완료 마킹의 함정" 재발 방지 원칙).
>
> [HARD] 아래 인수 기준은 GEARS 트리거/응답 쌍(Ubiquitous/While/When/Where + `shall`/`shall not`)으로
> 작성한다. 검증하는 내용은 이전 Given/When/Then 형태와 동일하며 표현 형식만 spec.md §4의 REQ와
> 일관되도록 GEARS로 통일했다.
>
> [HARD] REQ-MADM 번호는 spec.md §4의 001~035 완전 연속 재번호화(plan-auditor iteration 2 재감사 D1
> 대응)를 그대로 따른다. 구 번호 → 신 번호 대응표는 `progress.md` §E.1을 참조한다.

## Slice A — 닉네임 변경 기록 조회 UI

### AC-A1: 기록 목록 실 데이터 표시 (REQ-MADM-001, REQ-MADM-002)

**While** `NicknameChangeLog`에 변경 이력 행이 1건 이상 존재하는 상태에서, **When** 관리자가 닉네임 변경
기록 화면을 열면, 시스템 **shall** 회원 아이디/닉네임, 변경 전/후 닉네임, 변경 일시를 정확히 표시하고,
`changedByAdminId`가 채워진 행은 관리자에 의한 변경으로 표시한다.

### AC-A2: 페이지네이션 영속 (REQ-MADM-003)

**While** 기록이 1페이지 분량을 초과하는 상태에서, **When** 관리자가 다음 페이지로 이동한 뒤 URL을
새로고침하면, 시스템 **shall** 동일한 페이지의 데이터를 다시 표시한다(페이지 상태가 클라이언트 전용
상태로 사라지지 않는다).

## Slice B — 아이디/닉네임 차단 관리 UI

### AC-B1: 차단 등록 영속 (REQ-MADM-004, REQ-MADM-005)

**When** 관리자가 차단 관리 화면에서 종류(NICK_NAME)와 패턴을 입력해 등록을 제출한 뒤 페이지를
새로고침하면, 시스템 **shall** 등록한 패턴을 목록에 그대로 유지한다(DB `denied_identifiers` 행에
영속).

### AC-B2: 중복 등록 거부 (REQ-MADM-006)

**While** 이미 등록된 `(kind, pattern)` 조합이 존재하는 상태에서, **When** 관리자가 동일 조합을 다시
등록하려 시도하면, 시스템 **shall** 오류 메시지에 위반된 필드(`kind`, `pattern`)와 기존 등록된 값을
명시하여 표시하고, 목록에 중복 행을 생성하지 않는다(재조회로 확인).

### AC-B3: 삭제 영속 (REQ-MADM-007)

**When** 관리자가 목록의 항목 삭제를 실행한 뒤 새로고침하면, 시스템 **shall** 해당 항목이 더 이상
목록에 나타나지 않는 상태를 유지한다.

### AC-B4: 차단 등록의 실제 집행 확인 (REQ-MADM-004~007, 교차 확인)

**Where** 닉네임 패턴 하나가 차단 목록에 등록되어 있는 경우, **When** 그 패턴과 일치하는 닉네임으로
실제 회원가입을 시도하면(`packages/auth/src/signup.ts` 경로), 시스템 **shall** 가입을 거부한다 —
관리자 UI에서 등록한 값이 이미 존재하는 `signup.ts` 검증에 실제로 반영됨을 재확인하는 회귀 성격의
시나리오다(신규 로직 추가 없이 기존 백엔드가 정상 소비하는지 확인).

### AC-B5: 빈 패턴 제출 거부 (REQ-MADM-008)

**When** 관리자가 등록 폼에서 빈 패턴을 제출하면, 시스템 **shall** 클라이언트 측에서 제출을 차단한다.
**When** 클라이언트 검증을 우회해 빈 패턴이 서버에 도달하면, 시스템 **shall** 서버 측 검증(`min(1)`)
실패 사유를 화면에 그대로 노출한다(무음 실패 금지).

## Slice C — 회원 그룹 재배치 + 이미지 마크

### AC-C1: imageMark 저장·표시 (REQ-MADM-009, REQ-MADM-010)

**When** 관리자가 그룹 생성/수정 화면에서 imageMark 값을 입력해 저장한 뒤 그룹 목록 페이지를
새로고침하면, 시스템 **shall** 입력한 값을 그룹 목록의 썸네일/표시로 나타낸다(DB
`member_groups.imageMark`에 영속).

### AC-C2: 드래그앤드롭 순서 변경 영속 (REQ-MADM-011, REQ-MADM-012)

**While** 그룹 A, B, C가 순서대로 존재하는 상태에서, **When** 관리자가 C를 A 위로 드래그해 놓은 뒤
페이지를 새로고침하면, 시스템 **shall** 순서를 C, A, B로 유지한다(`listOrder`가 `admin.group.reorder`로
원자적으로 영속됨).

### AC-C3: 재배치 실패 롤백 (REQ-MADM-013)

**When** `admin.group.reorder` 요청이 서버에서 실패하는 상태에서 관리자가 드래그를 완료하면, 시스템
**shall** 화면을 직전 영속 순서로 롤백하고 오류를 표시한다(허위 성공 표시 금지).

### AC-C4: 키보드 재배치 + Escape 취소 (REQ-MADM-014)

**Where** 키보드 인터랙션이 가능한 환경인 경우, **When** 관리자가 재배치 컨트롤에 포커스한 상태에서
키보드로 순서를 변경하면, 시스템 **shall** `MenuItemDnDTree` 패턴과 동일하게 키보드 재배치를 지원한다.
**When** 순서 변경 도중 관리자가 Escape를 누르면, 시스템 **shall** 변경을 취소하고 직전 순서로 되돌린다.

## Slice D — 회원 설정 "기본 설정" 탭

### AC-D1: 탭 위치 및 필드 저장 (REQ-MADM-015, REQ-MADM-016)

**When** 관리자가 회원 설정 페이지를 열면, 시스템 **shall** "기본 설정"을 첫 번째 탭으로 표시한다.
**When** 관리자가 가입 허가 모드(허용/거부/가입키)를 저장한 뒤 새로고침하면, 시스템 **shall** 저장한
값을 그대로 유지한다.

### AC-D2: 가입키 모드 실 집행 (REQ-MADM-017)

**While** 가입 허가 모드가 "가입키 일치 시에만 허용"으로 설정되어 있고 유효한 키가 지정된 상태에서,
**When** 방문자가 잘못된(또는 없는) 키 파라미터로 회원가입을 시도하면, 시스템 **shall** 가입을
거부한다. **When** 방문자가 올바른 키로 시도하면, 시스템 **shall** 가입을 정상 진행한다.

### AC-D3: 인증 메일 유효기간 실 반영 (REQ-MADM-018)

**Where** 인증 메일 유효기간이 짧게(예: 1분) 설정되어 있는 경우, **When** 회원가입 후 그 시간이 지나
인증 링크를 클릭하면, 시스템 **shall** 토큰을 만료로 거부한다 — 설정값이 `EmailAuthToken` 만료
판정에 실제로 반영됨을 확인한다.

### AC-D4: 관리자 목록 프로필사진 노출 토글 (REQ-MADM-019)

**While** 프로필사진 노출 설정이 "끔"으로 저장된 상태에서, **When** 관리자가 `/admin/members` 회원
목록을 새로고침하면, 시스템 **shall** 프로필사진을 표시하지 않는다. 설정을 "켬"으로 되돌리면 시스템
**shall** 프로필사진을 다시 표시한다.

### AC-D5: 닉네임 변경 허용/기록 저장 토글 (REQ-MADM-020~022)

**While** 닉네임 변경 허용이 "끔"으로 저장된 상태에서, **When** 관리자 편집 화면에서 닉네임 변경을
시도하면, 시스템 **shall** 변경을 거부한다. **While** 허용이 "켬"이고 기록 저장이 "끔"으로 저장된
상태에서, **When** 닉네임을 변경하면, 시스템 **shall** 변경을 성공시키되 `NicknameChangeLog`에 새
행을 생성하지 않는다(재조회로 확인).

### AC-D6: 닉네임 특수문자/띄어쓰기 검증 실 반영 (REQ-MADM-023)

**While** 특수문자 허용이 "아니오"로 저장된 상태에서, **When** 특수문자가 포함된 닉네임으로 가입 또는
변경을 시도하면, 시스템 **shall** 요청을 거부한다. **While** 허용이 "예"이고 허용 문자가 지정된
상태에서, **When** 그 문자를 포함한 닉네임으로 시도하면, 시스템 **shall** 요청을 성공시킨다.

### AC-D7: 닉네임 중복 허용 설정 키 일치 확인 (REQ-MADM-024)

**When** 관리자가 "기본 설정" 탭에서 닉네임 중복 허용을 켜고 저장한 뒤 기존 "가입 설정" 탭을 열어
동일 필드를 확인하면, 시스템 **shall** 두 탭 모두 동일한 값(같은
`member.signup.allowDuplicateNickname` 키)을 표시한다 — 별도 키로 분기되지 않았음을 재조회로 확인한다.

### AC-D8: 비밀번호 보안수준 실 검증 (REQ-MADM-025)

**While** 비밀번호 보안수준이 "높음"(`VERY_STRONG`)으로 저장된 상태에서, **When** 숫자·특수문자가
없는 약한 비밀번호로 회원가입 또는 비밀번호 변경을 시도하면, 시스템 **shall** 요청을 거부한다.
**While** 보안수준이 "낮음"(`NORMAL`)으로 저장된 상태에서, **When** 동일한 약한 비밀번호로 시도하면,
시스템 **shall** 요청을 통과시킨다.

### AC-D9: Argon2id timeCost 조정 실 반영 + 안전 범위 클램프 (REQ-MADM-026)

**When** 관리자가 timeCost를 안전 범위 내 값(예: 4)으로 저장한 뒤 신규 회원가입으로 비밀번호 해시를
생성하면, 시스템 **shall** 생성된 PHC 해시 문자열의 `t=` 파라미터를 저장한 값과 일치시킨다. **When**
관리자가 안전 범위를 벗어난 값(예: 0 또는 100)을 저장 시도하면, 시스템 **shall** 요청을 거부한다
(§7-5 클램프).

### AC-D10: 자동 업그레이드 토글 실 반영 (REQ-MADM-027)

**While** 테스트 계정이 레거시 형식(비-Argon2id) 해시를 갖고 자동 업그레이드 토글이 "끔"으로 저장된
상태에서, **When** 그 계정으로 로그인에 성공하면, 시스템 **shall** `passwordHash`/`passwordAlgo`를
재해싱하지 않고 그대로 유지한다. **While** 토글이 "켬"으로 저장된 상태에서, **When** 동일 계정으로
다시 로그인하면, 시스템 **shall** 재해싱을 수행한다(기존 REQ-AUTH-014 동작 재현).

## Slice E — 이메일 호스트 관리

### AC-E1: 호스트 등록/삭제 영속 (REQ-MADM-028~031)

**When** 관리자가 이메일 호스트 관리 화면에서 `example.com`을 `DENY`로 등록해 저장한 뒤 페이지를
새로고침하면, 시스템 **shall** 등록한 항목을 정책과 함께 목록에 유지한다. **When** 관리자가 그 항목을
삭제한 뒤 새로고침하면, 시스템 **shall** 그 항목이 목록에서 사라진 상태를 유지한다.

### AC-E2: 화이트리스트 모드 실 집행 (REQ-MADM-032)

**While** `ALLOW` 정책으로 `trusted.com`만 등록된 상태에서, **When** `user@untrusted.com`으로
회원가입을 시도하면, 시스템 **shall** 가입을 거부한다. **When** `user@trusted.com`으로 시도하면,
시스템 **shall** 가입을 정상 진행한다.

### AC-E3: 블랙리스트 모드 실 집행 (REQ-MADM-033)

**While** `ALLOW` 정책 호스트가 없고 `DENY` 정책으로 `spam.com`만 등록된 상태에서, **When**
`user@spam.com`으로 회원가입을 시도하면, 시스템 **shall** 가입을 거부한다. **When**
`user@anything-else.com`으로 시도하면, 시스템 **shall** 가입을 정상 진행한다.

### AC-E4: 미설정 시 무제한 (REQ-MADM-034)

**Where** `ManagedEmailHost`에 등록된 행이 하나도 없는 경우, **When** 임의 도메인 이메일로 회원가입을
시도하면, 시스템 **shall not** 이메일 도메인을 이유로 가입을 거부한다(현재 동작과 동일).

### AC-E5: 거부 시 부분 생성 방지 (REQ-MADM-035)

**When** 이메일 호스트 정책으로 가입 시도가 거부되면, 시스템 **shall not** 그 이메일/아이디로 생성된
`User` 행을 DB에 남긴다(원자적 거부, 부분 생성 없음).

## 엣지 케이스

- 그룹이 0개이거나 1개뿐일 때 재배치 UI 진입 시 오류 없음.
- 차단 목록/이메일 호스트 목록이 비어 있을 때 관리자 화면이 빈 상태를 정상 표시.
- 닉네임 변경 기록이 0건일 때 목록 화면이 "기록 없음"을 표시하고 오류 없음.
- 동일 호스트를 `ALLOW`와 `DENY`로 동시에 등록 시도 — plan.md §7-4 확정 정책(ALLOW 우선)에 따라 결정된
  동작을 테스트로 고정.
- Argon2id timeCost를 범위를 벗어나게 API로 직접 호출(UI 우회) — 서버 측 Zod 검증이 거부.
- 닉네임 변경 허용이 꺼진 상태에서 회원 자신이 아닌 관리자가 강제로 닉네임을 바꾸는 경로(허용되어야
  하는지 여부는 run phase에서 "관리자는 정책과 무관하게 변경 가능" 여부를 확정하고 테스트로 고정).
- 인증 메일 유효기간을 매우 크게(예: 365일) 설정 — 상한 없이 허용할지 정책 확정 필요.
