# SPEC-LEGACY-PARITY-001 — design: M3 버튼 이미지 전체 범위 설계 결정

> Tier L 재판정(v0.3.0 — plan.md §A.0)으로 추가된 산출물. 이 문서는 구현 지침이 아니라
> **설계 결정의 기록**이다: 각 결정에 대해 후보, 선택, 근거, 되돌림 조건을 남긴다.
> WHAT/WHY는 spec.md가, 절차·순서는 plan.md가 소유한다 — 여기는 HOW의 정당화다.

## D1 — 버튼 필드 저장 형태 정착 (Q4)

**문제.** 같은 필드(`normalBtn`/`hoverBtn`/`activeBtn`)의 저장 표현이 3곳에서 서로 다르다
(`research.md` §1.4 (2)): 편집기 스타일 JSON(`{"color": "..."}`) /
`bundle-schema.ts:29-34` `{label, href, icon, target}` / 레거시 `varchar(255)` 파일명.
export→import 왕복이 현재 결함이다(REQ-SITE-011).

**후보.**

| 후보 | 내용 | 판단 |
|---|---|---|
| A. 이미지 참조형 | `{"image": "<file-storage 참조>", "alt": "..."}` 처럼 파일 저장소 참조를 값으로 | **채택 방향** |
| B. 순수 파일명 문자열 | 레거시 의미론 그대로 `varchar` 문자열 값 | 렌더에 필요한 URL 해석·alt·상태 매핑을 담을 수 없다 |
| C. 전체 스타일 JSON 확장 | 현 편집기 JSON을 확장해 이미지 키 추가 | 업로드 파이프라인(`packages/file`)의 산출물(참조)을 원문 JSON에 내장하는 형태가 되어 왕복 검증이 약해진다 |

**선택: A(이미지 참조형).** 근거: (1) REQ-SITE-010 공개 렌더링이 저장된 참조를 URL로 해석할
수 있어야 한다; (2) 레거시 `varchar(255)` 파일명 의미론과 양립 — 레거시 번들 import 시 파일명
값을 참조형으로 정규화하는 다리를 놓을 수 있다; (3) `Json?` 컬럼 정의 변경 없이 수용된다
(스키마 마이그레이션 0건 — plan.md §A.3).

**하위호환 규칙.** 레거시 번들 import(`apply.ts`)가 받은 문자열(파일명) 값은
`{"image": <문자열>}`로 정규화해서 수용한다. 레거시 실사용이 0이므로(`research.md` §1.4 (3))
실데이터 이전 비용은 없지만, 수용 규칙이 있어야 export 번들의 형태가 닫힌 집합으로 유지된다.
`bundle-schema.ts`는 정합화된 형태 외 값을 거부한다(AC-SITE-011 (2)).

**run-phase 확인 사항(결정 확정 조건).** M3 착수 시 편집기 텍스트영역의 **현재 저장값**을
조회한다 — 스타일 값(색상 등)의 실사용이 보이면 텍스트영역을 교체가 아니라 공존으로 바꾸고
spec.md HISTORY에 기록한다(이 축은 텍스트영역 운명이지 저장 형태가 아니다). 저장 형태 자체는
본 결정이 유지된다.

## D2 — 업로드 인프라: `packages/file` 재사용

**문제.** 3종 이미지 파일 업로드 경로를 어디에 두는가.

**결정.** 기존 `packages/file/src/` 인프라를 재사용한다 — `image-pipeline.ts`(이미지 검증·
처리), `storage/factory.ts`(저장소 추상), `server/actions.ts`(서버 액션), `attachment.ts`.
**신규 업로드 엔드포인트·신규 저장 추상을 만들면 범위 이탈이다**(spec.md §4.7).

**근거.** 업로드 인프라는 이미 존재하고 검증돼 있다. 새로 만드는 모든 것은 이 SPEC의 목적
(레거시 동등성)에 기여하지 않으면서 보안 표면(파일 검증, 경로 처리)을 늘린다.

**되돌림 조건.** `packages/file`의 인터페이스가 메뉴 버튼 이미지의 요구(3필드 독립 저장,
상태별 제거)를 수용하지 못하는 것이 **run-phase에 실제로 확인된 경우**에만, 그 격차를 spec.md
HISTORY에 기록하고 최소 확장을 설계한다 — 이 문서의 사전 승인이 아니다.

## D3 — 공개 렌더링: 상태별 표시

**문제.** `MenuRenderer.tsx`가 3종 상태 이미지를 어떻게 렌더하는가.

**결정.**

- **normal**: 이미지가 있으면 텍스트 라벨 대신 기본 표시(이미지가 라벨을 대체한다 — 라벨
  없는 빈 링크를 만들지 않는다, AC-SITE-010).
- **hover / active**: 해당 상호작용 상태에서 표시. 구현은 CSS 상태 스위치(동일 `<img>`의
  src 교체 또는 두 레이어 전환)를 우선한다 — JS 상태 추적 없이 브라우저 상태 선택자로
  해결 가능한지 먼저 확인한다.
- 이미지가 없는 아이템의 렌더는 **현행 그대로**다(텍스트 라벨) — 이 분기가 M2 특성화
  테스트(이미지 없는 기존 동작)로 보호된다.
- 변경은 아이템 **표시 계층에 한정**된다 — 중첩 트리 재귀(`MenuRenderer.tsx` 하위
  렌더)·`groupIds` ACL 필터(`:47-48`)·슬롯 선택 로직은 건드리지 않는다. 이 3동작은 M2
  특성화(AC-SITE-004~006)가 지키며, M3가 이 로직을 침범하면 특성화 테스트가 즉시 실패한다.

**근거.** 레거시는 normal/hover/active 3파일 업로드 모델이므로 뉴버전의 표시 모델도 상태
3분기여야 동등하다(REQ-SITE-010). 반면 렌더 구현 기술(CSS vs JS)은 동등성 요건이 아니므로
가장 단순한 수단을 택한다.

## D4 — 특성화 선행 순서 (구조적 제약)

**문제.** 테스트와 구현 변경의 순서.

**결정.** M2(승계 3동작 특성화) → M3(렌더러·편집기 변경) 순서는 선호가 아니라 **구조적
제약**이다(plan.md §A.2). 렌더러를 먼저 바꾸고 나중에 쓴 테스트는 변경 후 동작을 묘사할 뿐,
변경이 도입한 회귀를 잡지 못한다.

**증명 수단.** 커밋 순서로 증명한다 — M2 특성화 테스트 커밋이 `MenuRenderer.tsx` 변경
커밋보다 선행하는지 `git log`로 확인(acceptance.md DoD).

**문제.** 전체 범위 결정 후 Tier M이 여전히 맞는가.

파일 12~17, 3패키지에 걸친 데이터 형태 결정).

(3) 커밋 전략이 직접 main push에서 PR 흐름(manager-git)으로 변경(plan.md §A.6).

**되돌림 조건.** 범위가 다시 축소되는 경우(예: 공개 렌더링 제외 결정) §A.0의 수치를 다시
계산해 재판정한다 — 감사 결함은 과소·과대 양방향이므로.
