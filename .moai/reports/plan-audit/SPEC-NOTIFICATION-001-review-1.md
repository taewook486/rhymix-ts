D4. spec.md:L9 — Frontmatter field `priority: P2` does not conform to the MP-3 required enum (`critical`, `high`, `medium`, `low`). `P2` is a different priority taxonomy (numeric tier) not in the allowed value set. — Severity: major (independently sufficient for MP-3 FAIL; type/value mismatch)

D5. spec.md:L98 (REQ-NOTIF-026) — The requirement text mixes a non-binding "MAY... as an implicit side effect" clause with an EARS "(State-Driven)" label and a parenthetical "this is OPTIONAL (Where-pattern) and is not required for the MVP slice." A State-Driven EARS pattern requires "WHILE [condition], the [system] SHALL [response]" — using "MAY" instead of "SHALL" breaks strict EARS grammar even though the (State-Driven) tag is applied. This REQ is also absent from the Slice A EARS coverage line (spec.md:L164) and has no corresponding AC/EC reference in acceptance.md, leaving it both grammatically inconsistent and untraced. — Severity: minor (does not change the EARS-pattern-label-presence check used for MP-2 since all REQs do carry a five-pattern label, but it weakens Clarity/Testability/Traceability scores)

D6. acceptance.md:L113-121 (EC-3) — The edge case explicitly defers the expected behavior to implementation time ("구현 단계에서 결정") with two alternative outcomes presented as an OR ("건너뛴다 또는 생성하되 조회 불가능한 상태로 둠"). ## Recommendation

This SPEC cannot proceed to user approval in its current form. The following fixes are required before re-audit:

1. **Fix D1 (critical)**: Either define a REQ-NOTIF-040 entry in the appropriate layer (Settings & Subscription layer, 030-049 range, where it would slot in numerically) with concrete EARS-formatted content describing the preference-check behavior being cross-referenced, OR remove the "(see REQ-NOTIF-040)" citation from spec.md:L78 if no such requirement is actually needed (REQ-NOTIF-008 already fully states the preference-check behavior inline, so the cross-reference may simply be vestigial and removable).

2. **Fix D2 + D3 (critical)**: Add a `labels` field to the YAML frontmatter (spec.md:L1-16) as an array, e.g. `labels: [notification, comment, mention]`. Rename `created: 2026-06-20` to `created_at: 2026-06-20` (or `2026-06-20T00:00:00Z` for full ISO-8601 compliance) to match the MP-3 required field name exactly.

3. **Fix D4 (major)**: Change `priority: P2` (spec.md:L9) to one of the MP-3 allowed enum values (`critical`, `high`, `medium`, `low`). Given the SPEC's own "Phase 7 / P2" framing and dependency-completion status, `medium` or `high` appears to be the intended mapping — manager-spec should make this determination explicitly rather than leaving the legacy `P2` numeric tier in place.

4. **Fix D5 (minor)**: Revise REQ-NOTIF-026 (spec.md:L98) to either (a) convert it to a strict EARS State-Driven SHALL statement if it is meant to be a binding requirement for a future slice, or (b) move it out of the numbered REQ list entirely into Technical Approach / Open Questions framing if it is genuinely non-binding guidance, so the REQ list contains only SHALL/SHALL NOT statements per MP-2.

5. **Fix D6 (minor)**: Resolve EC-3 (acceptance.md:L113-121) to a single deterministic expected behavior (pick either "skip notification creation" or "create but mark unreachable") rather than leaving an OR-clause deferred to implementation time. If genuinely undecided, move it to the `## Open Questions` section of spec.md with a best-judgment determination (matching the pattern already used for Q1-Q9), rather than leaving it as an unresolved acceptance criterion.

6. **Fix D7 (minor)**: Add REQ-NOTIF-026 to the Slice A (or a future Slice) EARS coverage line in spec.md, and add a corresponding AC or EC entry in acceptance.md, or explicitly state in the Slices section that REQ-NOTIF-026 is deferred/out-of-scope-for-now with no current trace required.

After applying fixes 1-3 (the must-pass blockers), re-run this audit. Fixes 4-6 should also be applied before final approval to raise category scores, though they are not independently blocking under M5.
